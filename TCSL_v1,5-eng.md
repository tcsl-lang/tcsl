## 1. Introduction

TCSL (TextToCAD Scripting Language) is a declarative domain-specific language (DSL) for describing three-dimensional solid models of cabinet furniture and similar products. A TCSL program simultaneously serves as an executable model description, parametric documentation, and input for a Python/FreeCAD code generator.

A TCSL program passes through a transpiler that produces Python/FreeCAD code. The output is a parametric 3D model, a FreeCAD object tree with names suitable for a cost calculator, and an FCStd file.

The language is designed so that its code can be generated by a large language model (LLM) in stages: first base parameters, then derived values, then geometry, and finally exports with names for the cost calculator.

---

## 2. Design Priorities

Priorities are listed in descending order of importance.

**Priority 1 — Dimensional type safety.** Every numeric value participating in geometry must carry a unit of measurement. Dimensionless numbers are permitted only for dimensionless multipliers (type Scalar). The types Length (L¹), Area (L²), Volume (L³), and Angle form a closed algebra with compile-time verification.

**Priority 2 — Parametric integrity.** Changing a single base parameter (`input`) automatically recomputes all dependent (`let`) values. Manual duplication of formulas in comments is prohibited: formulas exist only in `let` expressions.

**Priority 3 — LLM-friendly syntax.** A minimal, regular grammar with no user-defined functions, no nested blocks, and no nested scopes. The only form of syntactic recursion is parenthesized subexpressions `(a + b) * c` in LET zones and in function arguments. Parenthesis nesting depth is bounded: implementations must support at least 16 levels; exceeding this limit produces error TCSL_E020. The four zones follow a fixed order that matches the LLM generation phases (parameters → derived → geometry → export).

**Priority 4 — GUI configurator readiness.** The runtime automatically builds a user interface from the list of `input` parameters. `let` parameters are hidden from end users but visible during debugging.

**Priority 5 — Cost calculator naming.** Exported objects receive names conforming to the cost calculator convention (`Element_Material_Number`) via the `export … as Identifier` syntax, eliminating manual mapping in comments.

**Priority 6 — Readability as documentation.** A TCSL program should read like a product specification: variable names are meaningful, comments are explanatory, structure is sequential.

**Priority 7 — Deterministic output.** Identical input data always produces identical geometry within the tolerances of the geometric kernel.

---

## 3. Conformance

An implementation is considered conformant to the TCSL v1.5 specification if it accepts all syntactically and semantically valid programs (sections 5–11), rejects all violations (section 14), and produces geometry matching the described semantics (sections 8–11) within the tolerances of the geometric kernel (default 0.001 mm).

---

## 4. Notation

The grammar is written in EBNF (ISO/IEC 14977) with the following conventions: `=` — definition, `,` — concatenation, `|` — alternation, `[ … ]` — optional element, `{ … }` — repetition (0 or more), `(* … *)` — EBNF comment, `"…"` — terminal, `?…?` — special sequence. In code examples, `#` begins a TCSL comment, `→` shows a computed value, and `…` denotes omitted code.

## 5. Lexical Structure

### 5.1. Encoding

Source files use UTF‑8 encoding with an optional BOM. Control characters (except TAB, CR, LF) are prohibited.

### 5.2. Whitespace and Lines

```ebnf
HT    = ?U+0009? ;                          (* horizontal tab *)
WS    = ( " " | HT ) , { " " | HT } ;      (* one or more whitespace characters *)
OptWS = { " " | HT } ;                      (* zero or more whitespace characters *)
```

Space (U+0020) and horizontal tab (U+0009) separate tokens. CR (U+000D), LF (U+000A), or the sequence CR+LF terminate a logical line. One logical line equals one instruction. Line continuation is not supported.

In the grammar, `WS` denotes mandatory whitespace (one or more characters) and `OptWS` denotes optional whitespace (zero or more characters). All grammar rules use precisely these two nonterminals.

### 5.3. Comments

```ebnf
Comment = "#" , { AnyCharacterExceptNewline } ;
```

A comment begins with `#` and extends to the end of the line. Multi-line comments do not exist. Blank lines and comment-only lines are permitted anywhere in the program and do not affect the current zone.

### 5.4. Identifiers

```ebnf
Identifier = Letter , { Letter | Digit | "_" } ;
Letter     = "A" | "B" | … | "Z" | "a" | "b" | … | "z" ;
Digit      = "0" | "1" | … | "9" ;
```

Case-sensitive, maximum length 64 characters. An identifier may not begin with a digit or underscore. An identifier may not match a reserved word or a reserved unit of measurement (section 5.5).

### 5.5. Reserved Words

Reserved words fall into two categories.

**Fully reserved** — prohibited as identifiers in any context:

```
input  let  export  as
box  plate  cylinder  sphere
translate  rotate  scale
union  cut  subtract  intersect
linear_pattern  circular_pattern
select_edges_by_axis  select_edges_by_length
select_edges_parallel  select_edges_at_height
select_faces_by_axis  select_faces_by_area
select_by_tag
fillet  chamfer  shell
tag
```

**Reserved units** — prohibited as identifiers in any context:

```
mm  cm  m  in  ft
mm2  cm2  m2  in2  ft2
mm3  cm3  m3  in3  ft3
deg  rad
```

Attempting to use a reserved word or unit as an identifier produces error TCSL_E008.

### 5.6. Numeric Literals

```ebnf
IntLiteral   = Digit , { Digit } ;
FloatLiteral = Digit , { Digit } , "." , Digit , { Digit } ;
NumberLiteral = FloatLiteral | IntLiteral ;
```

During parsing, `FloatLiteral` is checked first for correct resolution of the decimal point. Leading zeros are permitted (e.g., `016`). Exponential notation is not supported. Literals are always non-negative; negative values are expressed via the unary minus operator (sections 5.8, 9.1).

### 5.7. Units of Measurement

```ebnf
VolumeUnit = "mm3" | "cm3" | "m3" | "in3" | "ft3" ;
AreaUnit   = "mm2" | "cm2" | "m2" | "in2" | "ft2" ;
LengthUnit = "mm" | "cm" | "ft" | "in" | "m" ;
AngleUnit  = "deg" | "rad" ;
Unit       = VolumeUnit | AreaUnit | LengthUnit | AngleUnit ;
```

A unit is written after a number; the space between the number and the unit is optional (`800mm` and `800 mm` are equivalent).

**Conversion table — length (to mm):**

| Unit | Factor |
|------|--------|
| mm   | 1      |
| cm   | 10     |
| m    | 1000   |
| in   | 25.4   |
| ft   | 304.8  |

**Conversion table — area (to mm²):**

| Unit | Factor    |
|------|-----------|
| mm2  | 1         |
| cm2  | 100       |
| m2   | 1 000 000 |
| in2  | 645.16    |
| ft2  | 92 903.04 |

**Conversion table — volume (to mm³):**

| Unit | Factor        |
|------|---------------|
| mm3  | 1             |
| cm3  | 1 000         |
| m3   | 1 000 000 000 |
| in3  | 16 387.064    |
| ft3  | 28 316 846.592|

**Conversion table — angle (to deg):**

| Unit | Factor             |
|------|--------------------|
| deg  | 1                  |
| rad  | 180 / π ≈ 57.29578 |

#### 5.7.1. Longest Match Rule for Units

When a number and unit are written without a space (`100mm2`), the lexer applies the longest match rule: from all units that are a prefix of the remaining input, the longest one is selected. Check order:

1. Volume units (3+ characters): `mm3`, `cm3`, `in3`, `ft3`, then `m3`
2. Area units (3+ characters): `mm2`, `cm2`, `in2`, `ft2`, then `m2`
3. Length units: `mm`, `cm`, `ft`, `in`, then `m`
4. Angle units: `deg`, `rad`

If the character sequence following a number does not match any unit, it is treated as the beginning of the next token. If no space separates them, error TCSL_E018 is raised: "Unknown unit of measurement or missing space between number and identifier."

### 5.8. Dimensional and Dimensionless Literals

```ebnf
DimensionalLiteral   = NumberLiteral , OptWS , Unit ;
DimensionlessLiteral = NumberLiteral ;
Literal              = DimensionalLiteral | DimensionlessLiteral ;
```

Literals are always non-negative. Negative values are expressed via the unary minus operator at the expression level (sections 9.1, see the `Factor` rule). In the INPUT zone, where expressions are prohibited, negative values use a special syntax:

```ebnf
InputLiteral = [ "-" , OptWS ] , Literal ;
```

This is the sole exception: the minus sign before a literal in `input` is part of the literal, not an operator. Outside `input`, the minus sign is always a unary operator at the `Factor` level.

A dimensional literal is required for all values participating in geometric computations (constructor parameters, transformation arguments). A dimensionless literal is permitted only for the Scalar type (multipliers, counters).

### 5.9. Operators and Delimiters

```
=  |>  +  -  *  /  (  )  ,  $
```

The `=` operator is used in declarations (INPUT, LET, GEOMETRY). The `|>` operator is the pipeline. Arithmetic operators `+  -  *  /` are permitted in the LET zone and in function arguments within the GEOMETRY zone. `$` is used for tagging: `Constructor$Tag(...)`. Parentheses `(` `)` group function arguments and subexpressions. The comma `,` separates arguments.

## 6. Type System

### 6.1. Dimensional Types

The type system is based on the length dimension exponent *n*, where *n* ∈ {0, 1, 2, 3}. A separate angular axis also exists.

| Type     | Exponent | Description              | Example literal      |
|----------|----------|--------------------------|----------------------|
| Scalar   | L⁰       | Dimensionless quantity   | `3`, `0.5`           |
| Length   | L¹       | Linear dimension         | `732 mm`, `2.5 ft`   |
| Area     | L²       | Area                     | `10000 mm2`, `1 m2`  |
| Volume   | L³       | Volume                   | `5000000 mm3`        |
| Angle    | —        | Angular quantity (separate axis) | `90 deg`, `1.57 rad` |

### 6.2. Geometric Types

| Type      | Description                                  |
|-----------|----------------------------------------------|
| Geometry  | Solid body                                   |
| EdgeSet   | Set of edges (result of select_edges_*)      |
| FaceSet   | Set of faces (result of select_faces_*)      |

### 6.3. Arithmetic Compatibility Table

Rule: when multiplying, dimension exponents are added; when dividing, they are subtracted. The result must remain in the range 0–3; exceeding this range produces error TCSL_E015.

**Multiplication (`*`):**

| Left     | Right    | Result    | Example                              |
|----------|----------|-----------|--------------------------------------|
| Scalar   | Scalar   | Scalar    | `2 * 3` → `6`                       |
| Scalar   | Length   | Length    | `2 * board` → `32 mm`               |
| Scalar   | Area     | Area      | `2 * face_area` → `20000 mm2`       |
| Scalar   | Volume   | Volume    | `0.5 * vol` → `2500000 mm3`         |
| Scalar   | Angle    | Angle     | `2 * 45 deg` → `90 deg`             |
| Length   | Scalar   | Length    | `board * 2` → `32 mm`               |
| Length   | Length   | Area      | `width * depth` → Area              |
| Length   | Area     | Volume    | `height * floor_area` → Volume      |
| Area     | Scalar   | Area      | `face_area * 2` → `20000 mm2`       |
| Area     | Length   | Volume    | `floor_area * height` → Volume      |
| Volume   | Scalar   | Volume    | `vol * 3` → `15000000 mm3`          |
| Angle    | Scalar   | Angle     | `90 deg * 2` → `180 deg`            |
| Length   | Volume   | **TCSL_E015** | Result L⁴ — prohibited          |
| Area     | Area     | **TCSL_E015** | Result L⁴ — prohibited          |
| Area     | Volume   | **TCSL_E015** | Result L⁵ — prohibited          |
| Volume   | Length   | **TCSL_E015** | Result L⁴ — prohibited          |
| Volume   | Area     | **TCSL_E015** | Result L⁵ — prohibited          |
| Volume   | Volume   | **TCSL_E015** | Result L⁶ — prohibited          |
| Angle    | Length   | **TCSL_R001** | Incompatible axes               |
| Angle    | Area     | **TCSL_R001** | Incompatible axes               |
| Angle    | Volume   | **TCSL_R001** | Incompatible axes               |
| Angle    | Angle    | **TCSL_R001** | Incompatible axes               |

**Division (`/`):**

| Left     | Right    | Result    | Example                              |
|----------|----------|-----------|--------------------------------------|
| Scalar   | Scalar   | Scalar    | `6 / 3` → `2`                       |
| Length   | Scalar   | Length    | `732 mm / 2` → `366 mm`             |
| Length   | Length   | Scalar   | `inner_w / board` → Scalar          |
| Area     | Scalar   | Area      | `face_area / 2` → `5000 mm2`        |
| Area     | Length   | Length    | `face_area / width` → Length         |
| Area     | Area     | Scalar   | `a1 / a2` → Scalar                  |
| Volume   | Scalar   | Volume    | `vol / 3` → Volume                  |
| Volume   | Length   | Area      | `vol / height` → Area               |
| Volume   | Area     | Length    | `vol / floor_area` → Length          |
| Volume   | Volume   | Scalar   | `v1 / v2` → Scalar                  |
| Angle    | Scalar   | Angle     | `180 deg / 4` → `45 deg`            |
| Angle    | Angle    | Scalar   | `180 deg / 90 deg` → `2`            |
| Scalar   | Length   | **TCSL_E015** | Result L⁻¹ — prohibited         |
| Scalar   | Area     | **TCSL_E015** | Result L⁻² — prohibited         |
| Scalar   | Volume   | **TCSL_E015** | Result L⁻³ — prohibited         |
| Length   | Area     | **TCSL_E015** | Result L⁻¹ — prohibited         |
| Length   | Volume   | **TCSL_E015** | Result L⁻² — prohibited         |
| Area     | Volume   | **TCSL_E015** | Result L⁻¹ — prohibited         |

**Division by zero.** If the right operand of a division equals zero (whether as a literal or as a result of computation), error TCSL_R008 is raised. Implementations must check the divisor. If the divisor is a literal `0` or `0 mm` etc., the error may be raised at compile time; if the divisor is an expression, the error is raised at runtime.

**Addition / Subtraction (`+`, `-`):**

| Left     | Right    | Result    | Note                                 |
|----------|----------|-----------|--------------------------------------|
| Scalar   | Scalar   | Scalar    | Permitted                            |
| Length   | Length   | Length    | Permitted                            |
| Area     | Area     | Area      | Permitted                            |
| Volume   | Volume   | Volume    | Permitted                            |
| Angle    | Angle    | Angle     | Permitted                            |
| *Any other combination* | | **TCSL_R001** | Incompatible dimensions    |

### 6.4. Verification Functions (Pseudocode)

```python
def dim_exponent(t):
    return {"Scalar": 0, "Length": 1, "Area": 2, "Volume": 3}[t]

def type_from_exp(n):
    return {0: "Scalar", 1: "Length", 2: "Area", 3: "Volume"}[n]

def check_multiply(left, right):
    if left == "Angle" or right == "Angle":
        if left == "Scalar":  return "Angle"
        if right == "Scalar": return "Angle"
        raise "TCSL_R001"
    n = dim_exponent(left) + dim_exponent(right)
    if n > 3: raise "TCSL_E015"
    return type_from_exp(n)

def check_divide(left, right):
    if left == "Angle" and right == "Angle":  return "Scalar"
    if left == "Angle" and right == "Scalar": return "Angle"
    if left == "Angle": raise "TCSL_R001"
    if right == "Angle": raise "TCSL_R001"
    n = dim_exponent(left) - dim_exponent(right)
    if n < 0 or n > 3: raise "TCSL_E015"
    return type_from_exp(n)

def check_add_sub(left, right):
    if left != right: raise "TCSL_R001"
    return left
```

### 6.5. Numeric Model

All numeric values in TCSL are represented as 64-bit IEEE 754 binary64 floating-point numbers. No integer type exists: the literal `4` is represented as `4.0`. The result of any arithmetic operation is float64.

**Integer contexts.** Certain parameters semantically require an integer value: `count` in `linear_pattern` and `circular_pattern`. For these parameters, the implementation verifies that the value is integral (fractional part equals zero within tolerance ε = 1e-9). If the value is not integral, error TCSL_R009 is raised.

## 7. Program Structure — Four Zones

A TCSL program consists of four zones that must appear in strict order. Zone transitions are irreversible: a line from an earlier zone appearing after the parser has entered a later zone produces error TCSL_E005.

```ebnf
Program = { BlankOrComment }
          ZoneInput
          { BlankOrComment }
          ZoneLet
          { BlankOrComment }
          ZoneGeometry
          { BlankOrComment }
          ZoneExport
          { BlankOrComment } ;
```

Zone automaton:

```
ZONE_INPUT → ZONE_LET → ZONE_GEOMETRY → ZONE_EXPORT → END
```

Transitions are strictly unidirectional. Blank lines and comment-only lines do not change the current zone.

| Zone | Keyword | Purpose                                   | Runtime override |
|------|---------|-------------------------------------------|------------------|
| 1 — INPUT    | `input`  | Base parameters, literals only         | Yes (GUI, CLI, API, config) |
| 2 — LET      | `let`    | Derived parameters, expressions        | No (automatic recomputation) |
| 3 — GEOMETRY | *none*   | Solid construction, transformations    | No |
| 4 — EXPORT   | `export` | Output object declarations with names  | No |

A minimal valid program contains at least one GEOMETRY line and at least one EXPORT line. The INPUT and LET zones may be empty.

## 8. Zone 1 — INPUT

### 8.1. Syntax

```ebnf
ZoneInput   = { InputDecl { BlankOrComment } } ;
InputDecl   = "input" , WS , Identifier
              , OptWS , "=" , OptWS
              , [ "-" , OptWS ] , Literal
              , OptWS , [ Comment ] , Newline ;
```

The right-hand side of `input` contains only a literal (dimensional or dimensionless) with an optional leading minus. Arithmetic expressions, references to other identifiers, and function calls are prohibited in `input` (error TCSL_E012). The minus before a literal in `input` is part of the literal, not an operator; this is the only place, apart from the `Factor` rule, where a minus sign is permitted.

### 8.2. Semantics

Each `input` declares a named parameter with a type determined by its unit of measurement (or Scalar if no unit is present). The value is placed in the symbol table. Redeclaring the same identifier produces error TCSL_E006.

### 8.3. Runtime Override

The runtime environment may override any `input` before computation begins. Override sources (in priority order): GUI configurator, JSON/YAML configuration file, command-line arguments, API call. When overriding, the type must match the original; a type mismatch produces error TCSL_R006.

### 8.4. Example

```tcsl
# === ZONE 1: INPUT ===
input total_width   = 732 mm
input total_depth   = 550 mm
input side_height   = 900 mm
input board         = 16 mm
input back_panel_t  = 3 mm
input guide_w       = 13 mm
input niche_h       = 150 mm
input num_drawers   = 4
input gap           = 3 mm
input face_gap      = 2 mm
```

## 9. Zone 2 — LET

### 9.1. Syntax

```ebnf
ZoneLet     = { LetDecl { BlankOrComment } } ;
LetDecl     = "let" , WS , Identifier
              , OptWS , "=" , OptWS
              , Expression
              , OptWS , [ Comment ] , Newline ;

Expression  = Term , { OptWS , ( "+" | "-" ) , OptWS , Term } ;
Term        = Factor , { OptWS , ( "*" | "/" ) , OptWS , Factor } ;
Factor      = [ "-" , OptWS ] , Atom ;
Atom        = DimensionalLiteral
            | DimensionlessLiteral
            | Identifier
            | "(" , OptWS , Expression , OptWS , ")" ;
```

Unary minus is defined **only** at the `Factor` level. Literals within expressions are always non-negative. Parenthesis nesting depth is bounded (at least 16 levels); exceeding the limit produces error TCSL_E020.

### 9.2. Semantics

Each `let` declares a named derived parameter. The right-hand side is an arithmetic expression that may reference previously declared `input` and `let` identifiers. Referencing a not-yet-declared identifier produces error TCSL_E013.

Evaluation is single-pass, top to bottom. Cyclic dependencies are impossible by construction (references may only target previously defined identifiers).

The result type is determined by the arithmetic compatibility table (section 6.3). Incompatible operations produce compile-time errors.

If the right operand of a division equals zero (whether as a literal or as a result of computation), error TCSL_R008 is raised (see section 6.3).

### 9.3. External Override Prohibition

`let` parameters cannot be overridden externally. An override attempt produces error TCSL_E014. A `let` value is always deterministic given the `input` values.

### 9.4. Example

```tcsl
# === ZONE 2: LET ===
let inner_width     = total_width - 2 * board        # → 700 mm
let inner_depth     = total_depth - back_panel_t      # → 547 mm
let drawer_width    = inner_width - 2 * guide_w       # → 674 mm
let usable_height   = side_height - 2 * board - niche_h  # → 718 mm
let drawer_height   = usable_height / num_drawers - gap  # → 176.5 mm
let face_width      = drawer_width - 2 * face_gap     # → 670 mm
let face_height     = drawer_height - face_gap         # → 173.5 mm

# Z-coordinates (cascade from bottom up)
let z_bottom_base   = 0 mm
let z_bottom_top    = z_bottom_base + board            # → 16 mm
let z_niche_top     = z_bottom_top + niche_h           # → 166 mm
let z_drawer1_base  = z_niche_top + gap                # → 169 mm

# Area and volume (demonstrating L² and L³)
let floor_area      = inner_width * inner_depth        # → 382900 mm2  (Area)
let cabinet_volume  = floor_area * usable_height       # → Volume
```

## 10. Zone 3 — GEOMETRY

### 10.1. Syntax

```ebnf
ZoneGeometry     = { GeometryAssign { BlankOrComment } } ;
GeometryAssign   = Identifier
                   , OptWS , "=" , OptWS
                   , GeometryExpr
                   , OptWS , [ Comment ] , Newline ;

GeometryExpr     = GeometryAtom , { OptWS , "|>" , OptWS , PipelineStep } ;
GeometryAtom     = ConstructorCall | BooleanOp | Identifier ;

ConstructorCall  = Constructor , [ "$" , Identifier ]
                   , OptWS , "(" , OptWS , ArgList , OptWS , ")" ;
Constructor      = "box" | "plate" | "cylinder" | "sphere" ;

PipelineStep     = TransformCall | PatternCall | SelectorCall
                 | ModifierCall | BooleanPipeCall | TagCall ;

TransformCall    = ( "translate" | "rotate" | "scale" )
                   , OptWS , "(" , OptWS , ArgList , OptWS , ")" ;
PatternCall      = ( "linear_pattern" | "circular_pattern" )
                   , OptWS , "(" , OptWS , ArgList , OptWS , ")" ;
SelectorCall     = SelectorName
                   , OptWS , "(" , OptWS , ArgList , OptWS , ")" ;
SelectorName     = "select_edges_by_axis" | "select_edges_by_length"
                 | "select_edges_parallel" | "select_edges_at_height"
                 | "select_faces_by_axis" | "select_faces_by_area"
                 | "select_by_tag" ;
ModifierCall     = ( "fillet" | "chamfer" | "shell" )
                   , OptWS , "(" , OptWS , ArgList , OptWS , ")" ;
```

### 10.2. Constructors

| Constructor | Parameters                       | Parameter types            | Result   |
|-------------|----------------------------------|---------------------------|----------|
| `box`       | `width`, `depth`, `height`       | Length, Length, Length     | Geometry |
| `plate`     | `width`, `depth`, `height`       | Length, Length, Length     | Geometry |
| `cylinder`  | `radius`, `height`               | Length, Length             | Geometry |
| `sphere`    | `radius`                         | Length                    | Geometry |

`plate` is a semantic alias for `box`, intended for parts where one dimension (`height`) is significantly smaller than the other two (panels, shelves, tops, facades). Geometrically, `plate` and `box` are identical; the distinction is purely documentary:

- `box` — volumetric parts (side panels, posts, blocks, rails).
- `plate` — flat parts (shelves, countertops, back panels, drawer fronts).

The transpiler may use the constructor as a hint for selecting stock type in the cost calculator: `plate` → sheet material, `box` → lumber or panel stock. Implementations are not required to distinguish them; this is a recommendation.

All parameters of both constructors must be strictly positive (> 0); violation produces error TCSL_R002.

### 10.3. Transformations

| Function    | Parameters                                   | Types                     | Input    | Output   |
|-------------|----------------------------------------------|---------------------------|----------|----------|
| `translate` | `x`, `y`, `z`                                | Length, Length, Length     | Geometry | Geometry |
| `rotate`    | `angle`, `ax`, `ay`, `az`, `cx`, `cy`, `cz`  | Angle, Scalar×3, Length×3 | Geometry | Geometry |
| `scale`     | `sx`, `sy`, `sz`                             | Scalar, Scalar, Scalar    | Geometry | Geometry |

For `rotate`: `ax, ay, az` — rotation axis components (normalized automatically); `cx, cy, cz` — center of rotation (defaults to `0 mm, 0 mm, 0 mm`).

### 10.4. Boolean Operations

| Function     | Min arity | Max arity    | Input       | Output   | Description    |
|--------------|-----------|--------------|-------------|----------|----------------|
| `union`      | 2         | unbounded    | Geometry    | Geometry | Union          |
| `intersect`  | 2         | unbounded    | Geometry    | Geometry | Intersection   |
| `cut`        | 2         | 2            | Geometry    | Geometry | Subtraction    |
| `subtract`   | 2         | 2            | Geometry    | Geometry | Alias for `cut`|

#### 10.4.1. Boolean Operation Arity

Each boolean operation has a minimum and maximum arity (total operand count, including the implicit left operand in a pipeline).

**Standalone form:** all operands are listed explicitly in parentheses.
```tcsl
result = union(A, B, C)         # 3 operands — OK
result = cut(A, B)              # 2 operands — OK
result = cut(A, B, C)           # 3 operands — ERROR TCSL_E021
```

**Pipeline form:** the first operand comes from the pipeline (implicit), the rest are in parentheses.
```tcsl
result = A |> union(B, C)       # 3 operands (1 implicit + 2 explicit) — OK
result = A |> cut(B)            # 2 operands (1 implicit + 1 explicit) — OK
result = A |> cut(B, C)         # 3 operands — ERROR TCSL_E021
```

Arity violation produces error TCSL_E021.

**EBNF for boolean operations:**

```ebnf
(* Standalone form: all operands explicit *)
BooleanOp        = BooleanMultiOp | BooleanBinaryOp ;

BooleanMultiOp   = ( "union" | "intersect" )
                   , OptWS
                   , "(" , OptWS
                   , Identifier , OptWS , "," , OptWS , Identifier
                   , { OptWS , "," , OptWS , Identifier }
                   , OptWS , ")" ;

BooleanBinaryOp  = ( "cut" | "subtract" )
                   , OptWS
                   , "(" , OptWS
                   , Identifier , OptWS , "," , OptWS , Identifier
                   , OptWS , ")" ;

(* Pipeline form: first operand implicit from pipe *)
BooleanPipeCall  = BooleanPipeMulti | BooleanPipeBinary ;

BooleanPipeMulti = ( "union" | "intersect" )
                   , OptWS
                   , "(" , OptWS
                   , Identifier
                   , { OptWS , "," , OptWS , Identifier }
                   , OptWS , ")" ;

BooleanPipeBinary = ( "cut" | "subtract" )
                    , OptWS
                    , "(" , OptWS
                    , Identifier
                    , OptWS , ")" ;
```

### 10.5. Patterns

| Function           | Parameters                                 | Types                              | Input    | Output   |
|--------------------|--------------------------------------------|------------------------------------|----------|----------|
| `linear_pattern`   | `count`, `dx`, `dy`, `dz`                 | Scalar, Length, Length, Length      | Geometry | Geometry |
| `circular_pattern` | `count`, `angle`, `cx`, `cy`, `cz`, `ax`, `ay`, `az` | Scalar, Angle, Length×3, Scalar×3 | Geometry | Geometry |

`count` ≥ 2 (integer, verified per section 6.5 rules; non-integer value produces error TCSL_R009, value < 2 produces error TCSL_R002); `linear_pattern` creates `count` copies with step `(dx, dy, dz)` and unions them; `circular_pattern` creates `count` copies with uniform or explicit angular step around axis `(ax, ay, az)` through center `(cx, cy, cz)`.

### 10.6. Selectors

| Function                 | Parameters                | Types                | Input    | Output   |
|--------------------------|--------------------------|----------------------|----------|----------|
| `select_edges_by_axis`   | `axis`                   | Enum Axis            | Geometry | EdgeSet  |
| `select_edges_by_length` | `min`, `max`             | Length, Length        | Geometry | EdgeSet  |
| `select_edges_parallel`  | `dx`, `dy`, `dz`         | Scalar, Scalar, Scalar | Geometry | EdgeSet |
| `select_edges_at_height` | `z`, `tolerance`         | Length, Length        | Geometry | EdgeSet  |
| `select_faces_by_axis`   | `axis`, `keep`           | Enum Axis, Enum Keep | Geometry | FaceSet  |
| `select_faces_by_area`   | `min`, `max`             | Area, Area           | Geometry | FaceSet  |
| `select_by_tag`          | `name`, `expect`         | Identifier, Enum Expect | Geometry | EdgeSet or FaceSet |

An empty selector result produces error TCSL_R005 (runtime).

**Updated `select_by_tag` semantics:** the `expect` parameter is mandatory and determines the expected result type at static analysis time:

- `expect = edges` → result type is `EdgeSet`; if the tag was created with `scope = faces` or `scope = all`, only edges are selected.
- `expect = faces` → result type is `FaceSet`; if the tag was created with `scope = edges` or `scope = all`, only faces are selected.

If no elements of the requested type are found for the tag, error TCSL_R005 is raised (runtime).

### 10.7. Modifiers

| Function  | Parameters          | Types               | Input    | Output   |
|-----------|---------------------|----------------------|----------|----------|
| `fillet`  | `radius`            | Length               | EdgeSet  | Geometry |
| `chamfer` | `size`              | Length               | EdgeSet  | Geometry |
| `shell`   | `thickness`, `kind` | Length, Enum Kind    | FaceSet  | Geometry |

`kind` accepts values `inward` or `outward` (default: `inward`).

### 10.8. Tagging

Two syntaxes are available:

**Infix (via `$`):**
```tcsl
side = box$Side(width = board, depth = total_depth, height = side_height)
```

**Pipeline (via `tag()`):**
```tcsl
side = box(width = board, depth = total_depth, height = side_height) |> tag(Side, scope = edges)
```

```ebnf
TagCall     = "tag"
              , OptWS
              , "(" , OptWS , TagArgList , OptWS , ")" ;

TagArgList  = Identifier                              (* tag name *)
              , [ OptWS , "," , OptWS
                  , "scope" , OptWS , "=" , OptWS
                  , Identifier                        (* enum Scope value *)
                ] ;
```

The `scope` parameter is an enumeration: `all`, `edges`, `faces` (default: `all`). The first argument `name` is an identifier (tag name). The second argument `scope` is an optional named parameter with an enumerated value of type Scope.

### 10.9. Pipeline

The `|>` operator is left-associative. The entire pipeline must be written on a single logical line. The type of the left operand determines the permissible right-hand functions:

| Left type | Permissible right-hand functions                                             |
|-----------|-----------------------------------------------------------------------------|
| Geometry  | translate, rotate, scale, union, cut, subtract, intersect, linear_pattern, circular_pattern, select_*, tag |
| EdgeSet   | fillet, chamfer                                                             |
| FaceSet   | shell                                                                       |

Violating the compatibility table produces error TCSL_R003.

### 10.10. Arithmetic in Arguments

Inside function arguments, arithmetic expressions with references to `input` and `let` identifiers are permitted:

```tcsl
shelf = box(width = inner_width, depth = inner_depth - 10 mm, height = board)
```

Bare arithmetic assignment (without a constructor or function) in the GEOMETRY zone is prohibited — error TCSL_E002.

#### 10.10.1. Argument Order

In any function's argument list, two styles are permitted:

**Purely positional:** all arguments without names, order determined by the function signature.
```tcsl
box(100 mm, 50 mm, 16 mm)
```

**Purely named:** all arguments with names, order is arbitrary.
```tcsl
box(height = 16 mm, width = 100 mm, depth = 50 mm)
```

**Mixed style:** positional arguments precede named arguments. After the first named argument, all subsequent arguments must be named. Violation produces error TCSL_E019.

```tcsl
rotate(90 deg, ax = 0, ay = 0, az = 1, cx = 0 mm, cy = 0 mm, cz = 0 mm)  # OK
rotate(90 deg, 0, ay = 0, az = 1, cx = 0 mm, cy = 0 mm, cz = 0 mm)       # OK
rotate(ax = 0, 90 deg, 0, az = 1)                                          # ERROR E019
```

**EBNF for argument lists:**

```ebnf
ArgList         = AllPositional
                | AllNamed
                | MixedArgs ;

AllPositional   = PositionalArg , { OptWS , "," , OptWS , PositionalArg } ;

AllNamed        = NamedArg , { OptWS , "," , OptWS , NamedArg } ;

MixedArgs       = PositionalArg , { OptWS , "," , OptWS , PositionalArg }
                  , OptWS , "," , OptWS
                  , NamedArg , { OptWS , "," , OptWS , NamedArg } ;

NamedArg        = Identifier , OptWS , "=" , OptWS , ArgValue ;

PositionalArg   = ArgValue ;

ArgValue        = Expression ;
```

## 11. Zone 4 — EXPORT

### 11.1. The Naming Problem

The TextToCAD cost calculator determines the material and accounting unit of a part by the object name in the FreeCAD tree. The naming convention is: `Element_Material_Number` (e.g., `Side_PB16mm_1`, `BackPanel_HDF3mm_1`, `Front_MDF19mm_2`). TCSL variables use readable names (`cabinet_left_side`) that are not suitable for the calculator. Prior to version 1.4, the mapping existed only in comments, which caused four problems: comments are invisible to the parser; the name is duplicated in three places (code, comment, FreeCAD tree); exported objects receive a `TCSL_<var>` prefix that breaks the calculator; and there is a conflict between code readability and calculator requirements.

### 11.2. Solution: `export … as Identifier`

The `export … as Identifier` syntax allows a single line to specify both the program identifier (for TCSL references) and the FreeCAD tree object name (for the calculator).

### 11.3. Syntax

```ebnf
ZoneExport  = ExportDecl , { BlankOrComment | ExportDecl } ;
ExportDecl  = "export" , WS , Identifier
              , [ WS , "as" , WS , Identifier ]
              , OptWS , [ Comment ] , Newline ;
```

Parsing the rule:

- `export panel` — exports the object `panel`; in the FreeCAD tree it receives the name `TCSL_panel` (default behavior, backward compatible with v1.3).
- `export panel as Side_PB16mm_1` — exports the object `panel`; in the FreeCAD tree it receives the name `Side_PB16mm_1` (without the `TCSL_` prefix).

### 11.4. Rules

**Rule 11.4.1 — Type.** The exported identifier must have type `Geometry`. Attempting to export `Length`, `Area`, `Volume`, `Scalar`, `Angle`, `EdgeSet`, or `FaceSet` produces error TCSL_R004.

**Rule 11.4.2 — Definedness.** The exported identifier must be defined in the GEOMETRY zone. Referencing an undefined identifier produces error TCSL_E013.

**Rule 11.4.3 — At least one export.** A program without at least one `export` line produces error TCSL_R007.

**Rule 11.4.4 — Unique `as` names.** All `as` names within a program must be unique. Duplication produces error TCSL_E016.

**Rule 11.4.5 — Unique exported identifiers.** The same `Geometry` identifier may not be exported twice. Duplication produces error TCSL_E017.

**Rule 11.4.6 — `as` identifier format.** The `as` identifier follows the same lexical rules as a regular Identifier (section 5.4): ASCII letters, digits, underscore, maximum 64 characters. Cyrillic characters, spaces, and special characters are prohibited. This guarantees compatibility with FreeCAD's internal `Name` property (as opposed to `Label`).

**Rule 11.4.7 — Material warning (optional).** An implementation may issue warning TCSL_W001 if the `as` identifier does not contain a substring matching a known material keyword (e.g., `PB`, `HDF`, `MDF`, `HPL`, `Glass`, `Metal`, `Plywood`, `LDSP`, `DVP`). This is a warning, not an error — the program remains valid.

### 11.5. Code Generation Semantics

The transpiler uses the `as` identifier when generating Python/FreeCAD code as follows:

```python
# Without as:  export panel
panel.Label = "TCSL_panel"

# With as:     export panel as Side_PB16mm_1
panel.Label = "Side_PB16mm_1"
```

For FreeCAD: `Label` is the display name in the model tree; `Name` is the internal name (set at object creation, may match Label). The transpiler sets both.

### 11.6. Interaction with the Cost Calculator

The cost calculator parses object names from the FreeCAD tree using the pattern:

```
<Element>_<Material><Thickness><Unit>_<Number>
```

Examples:

| `as` identifier        | Element    | Material  | Thickness/Unit | Number |
|------------------------|------------|-----------|----------------|--------|
| `Side_PB16mm_1`        | Side       | PB        | 16mm           | 1      |
| `BackPanel_HDF3mm_1`   | BackPanel  | HDF       | 3mm            | 1      |
| `Front_MDF19mm_2`      | Front      | MDF       | 19mm           | 2      |
| `Shelf_PB16mm_3`       | Shelf      | PB        | 16mm           | 3      |
| `Countertop_HPL38mm_1` | Countertop | HPL       | 38mm           | 1      |

### 11.7. Complete EXPORT Zone Example

```tcsl
# === ZONE 4: EXPORT ===
export cabinet_left_side   as Side_PB16mm_1
export cabinet_right_side  as Side_PB16mm_2
export cabinet_bottom      as Bottom_PB16mm_1
export cabinet_top         as Top_PB16mm_1
export back_panel          as BackPanel_HDF3mm_1
export shelf_1             as Shelf_PB16mm_1
export shelf_2             as Shelf_PB16mm_2
export drawer_front_1      as Front_MDF19mm_1
export drawer_front_2      as Front_MDF19mm_2

```

## 13. Enumerations

### 13.1. Axis

```
Axis = "X" | "Y" | "Z"
```

Used in `select_edges_by_axis`, `select_faces_by_axis`.

### 13.2. Keep

```
Keep = "positive" | "negative" | "both"
```

Used in `select_faces_by_axis`. `positive` — faces with normals in the positive axis direction; `negative` — in the negative direction; `both` — both directions.

### 13.3. Kind

```
Kind = "inward" | "outward"
```

Used in `shell`. `inward` — shell inward (volume decreases); `outward` — outward.

### 13.4. Scope

```
Scope = "all" | "edges" | "faces"
```

Used in `tag`. Determines which geometric elements are marked with the tag.

### 13.5. Expect

```
Expect = "edges" | "faces"
```

Used in `select_by_tag`. Determines the expected output set type. Enables the static type analyzer to unambiguously determine the result type of `select_by_tag` without executing the program.

### 15.10. Complete Assembly — Cabinet with Four Drawers

```tcsl
# ===============================
# ZONE 1: INPUT — base parameters
# ===============================
input total_width   = 732 mm
input total_depth   = 550 mm
input side_height   = 900 mm
input board         = 16 mm
input back_panel_t  = 3 mm
input guide_w       = 13 mm
input niche_h       = 150 mm
input num_drawers   = 4
input gap           = 3 mm
input face_gap      = 2 mm
input front_board   = 19 mm

# ===============================
# ZONE 2: LET — derived parameters
# ===============================
let inner_width     = total_width - 2 * board
let inner_depth     = total_depth - back_panel_t
let drawer_width    = inner_width - 2 * guide_w
let usable_height   = side_height - 2 * board - niche_h
let drawer_step     = usable_height / num_drawers
let drawer_height   = drawer_step - gap
let face_width      = drawer_width - 2 * face_gap
let face_height     = drawer_height - face_gap

# Z cascade
let z_bot           = 0 mm
let z_bot_top       = z_bot + board
let z_niche_top     = z_bot_top + niche_h
let z_d1            = z_niche_top + gap
let z_d2            = z_d1 + drawer_step
let z_d3            = z_d2 + drawer_step
let z_d4            = z_d3 + drawer_step
let z_top_base      = side_height - board

# ===============================
# ZONE 3: GEOMETRY
# ===============================

# Side panels
left_side  = box(width = board, depth = total_depth, height = side_height)
right_side = box(width = board, depth = total_depth, height = side_height) |> translate(x = total_width - board, y = 0 mm, z = 0 mm)

# Horizontal panels
bottom     = box(width = inner_width, depth = total_depth, height = board) |> translate(x = board, y = 0 mm, z = z_bot)
top_panel  = box(width = inner_width, depth = total_depth, height = board) |> translate(x = board, y = 0 mm, z = z_top_base)

# Back panel
back_panel = box(width = inner_width, depth = back_panel_t, height = side_height - 2 * board) |> translate(x = board, y = total_depth - back_panel_t, z = z_bot_top)

# Drawer fronts
front_1    = box(width = face_width, depth = front_board, height = face_height) |> translate(x = board + guide_w + face_gap, y = 0 mm - front_board, z = z_d1 + face_gap)
front_2    = box(width = face_width, depth = front_board, height = face_height) |> translate(x = board + guide_w + face_gap, y = 0 mm - front_board, z = z_d2 + face_gap)
front_3    = box(width = face_width, depth = front_board, height = face_height) |> translate(x = board + guide_w + face_gap, y = 0 mm - front_board, z = z_d3 + face_gap)
front_4    = box(width = face_width, depth = front_board, height = face_height) |> translate(x = board + guide_w + face_gap, y = 0 mm - front_board, z = z_d4 + face_gap)

# ===============================
# ZONE 4: EXPORT
# ===============================
export left_side   as Side_PB16mm_1
export right_side  as Side_PB16mm_2
export bottom      as Bottom_PB16mm_1
export top_panel   as Top_PB16mm_1
```

## 18. Design Rationale

### 18.1. Why `input` + `let` (Rather Than a Single `input` with Expressions)?

Separating `input` (literals, externally overridable) and `let` (expressions, automatically recomputed) solves three problems: the GUI configurator automatically builds an interface from only `input` parameters; desynchronization errors (when the LLM updates a base parameter but forgets to recompute a dependent one) are eliminated by construction; responsibility is clearly divided (the human specifies the foundation, formulas compute the rest).

### 18.2. Why Four Zones (Rather Than Three)?

Separating `input` and `let` into distinct zones (rather than allowing free interleaving in one zone) provides a strict finite automaton with irreversible transitions. This simplifies error diagnostics (error codes unambiguously identify the zone), matches the four LLM generation phases, and allows extracting all `input` parameters with a simple pass through to the first `let`.

### 18.3. Why a Full Dimension System (Area, Volume)?

The hybrid approach (Area only, v1.2) solved the immediate problem but was inconsistent: if L × L is permitted, then L × L × L is a natural extension. The full L⁰–L³ system with compile-time checking catches errors impossible in v1.2 (e.g., `volume * height`) and makes the language suitable for material volume calculations.

### 18.4. Why `export … as Identifier` (Rather Than a String Literal)?

A string literal (`export panel as "Side_PB16mm_1"`) would require introducing a new lexical element (quotation marks) unique to a single construct. An identifier follows existing lexical rules, preserving language uniformity. The ASCII restriction guarantees compatibility with FreeCAD's internal `Name` property (which accepts only ASCII). Material keyword validation is implemented as a warning, not an error, leaving flexibility for non-standard conventions.

### 18.5. Why Are Literals Always Non-Negative?

In v1.4, unary minus could appear in two places: inside the literal (`DimensionalLiteral = ["-"], NumberLiteral, Unit`) and before an atom in an expression (`Factor = ["-"], Atom`). This created ambiguity: `-16 mm` admitted two parses — literal `(-16) mm` and unary operation `-(16 mm)`. In v1.5, the minus within literals is removed; negation exists in exactly two non-overlapping contexts: `InputDecl` (before a literal in `input`) and `Factor` (before an atom in expressions).

### 18.6. Why Are Units Reserved as Identifiers?

In v1.4, units (`mm`, `cm`, `m`, etc.) were valid identifiers, permitting code like `let mm = 5 mm`. This created an irresolvable conflict: does `mm` after a number denote a unit or an identifier? In v1.5, all units are included in the reserved word list, eliminating the overlap between lexical classes.

### 18.7. Why Does `select_by_tag` Require the `expect` Parameter?

In v1.4, the return type of `select_by_tag` depended on how the tag was created (with `scope = edges` or `scope = faces`). The static analyzer could not determine the type without executing the program. The mandatory `expect` parameter makes the result type explicit and verifiable at compile time.

### 18.8. Why float64 Without an Integer Type?

A single numeric model (float64) simplifies implementation and eliminates the need for type conversion rules. Integer contexts (`count` in patterns) are verified semantically — the value must be integral within tolerance ε.

## Localization Notes

Here is a summary of all adaptations made during the English localization, beyond straightforward translation.

**Cost calculator naming convention.** The original Russian specification used Cyrillic-transliterated names like `Bok_LDSP16mm_1` (Bok = Side panel, LDSP = laminated particleboard), `Zadstena_DVP3mm_1` (Zadstena = Back wall, DVP = hardboard), and `Fasad_MDF19mm_1` (Fasad = Facade/Front). For the international edition, these are replaced with English equivalents following the same `Element_Material_Number` pattern: `Side_PB16mm_1` (PB = particleboard), `BackPanel_HDF3mm_1` (HDF = high-density fiberboard), `Front_MDF19mm_1`. The `as` identifier syntax and rules are unchanged — only the example values are localized. Implementations supporting both Russian and international users should document both naming vocabularies in their material keyword list (Rule 11.4.7).

**Material keyword list.** The TCSL_W001 warning's known material keywords were expanded from the original Russian-focused list (`LDSP`, `DVP`, `MDF`, `HPL`, `Steklo`, `Metal`) to include international abbreviations: `PB` (particleboard), `HDF` (high-density fiberboard), `MDF`, `HPL`, `Glass`, `Metal`, `Plywood`. Implementations should treat this list as extensible and configurable.

**Variable names in examples.** Russian-flavored variable names like `fasad_board`, `z_dno_bot`, `z_dno_top`, `back_board` were replaced with self-explanatory English equivalents: `front_board`, `z_bottom_base`, `z_bottom_top`, `back_panel_t`. The `_t` suffix denotes thickness where disambiguation is needed.

**Zone comments in code examples.** Comments like `# === ЗОНА 1: INPUT ===` were translated to `# === ZONE 1: INPUT ===` throughout.

**Prose style.** Technical terms were aligned with FreeCAD's English API terminology (e.g., `Label` and `Name` properties, `solid body` for Geometry type). Section headings and rule names use standard English technical writing conventions.

**No specification changes.** The translation introduces zero changes to the language syntax, grammar, type system, error codes, or semantics. The EBNF grammar and TextMate grammar files are language-neutral and require no modifications. A TCSL program valid under the Russian specification is valid under the English specification, and vice versa — the specification language affects only documentation and example naming conventions.
